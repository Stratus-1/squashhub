# Audit: SportyHQ-style positional Swiss vs current SquashHub Swiss (Riverside pilot)

Research only. No code, data or publish changes until you approve a phase.

## What SquashHub does today

- Round 1 (`engine-service.swissFirstRound`): seeds 1 v N, 2 v N-1. With an odd field the lowest seed gets the bye. This already matches SportyHQ round 1.
- Rounds 2+ (`nextSwissRound` -> `contract.swissRound`): the **whole round** is paired at once from the standings. The pairing is score-group / greedy, with no repeat opponents. In `position_swap` mode, points are zeroed, so players are paired in order down the current position list (1v2, 3v4…). That is not a fixed slot map.
- Gate (`swiss-round-gate.ts`, plus the server guard `guard_swiss_round_progression`): Round N+1 can only be created after every Round N match is final, and only by an admin action (`swiss-generate.ts`). Nothing happens straight after a single result.
- Standings (`swiss-standings.ts`): the default is wins, then Buchholz, then Sonneborn-Berger, then seed. `position_swap` (switched on for Uitsig's Swiss divisions) works like a ladder: the winner takes the better of the two positions. This is close to the "loser of 1v16 drops to 16" idea, but it is a standings rule, not a draw rule.
- Display: `swiss-progression.ts` and `SwissProgressionView.tsx` replay `swissTable` round by round. This is the Riverside pilot flag `tournament_swiss_progression_view` in `club_beta_features`.
- There is an existing `mapped` stage kind (explicit "A1 v B1" units, validated in `contract.ts`). It is a useful model, but it only maps pool positions, not round-to-round slots.

## How SportyHQ Swiss Draw differs

From the official SportyHQ help page: fixed slots, where the winner of a match takes the better slot and the loser the worse slot for the next round. For example, the 1v16 loser goes to slot 16. That is **neither** conventional Swiss (dynamic score groups, Buchholz) **nor** Monrad (a placement bracket where winners meet winners). It is a deterministic position map:

```text
Round r match k (slots s_hi, s_lo)  --winner-->  slot W[r][k]  --loser-->  slot L[r][k]
Round r+1 pairs fixed slot pairs (e.g. 1v2? 1v4? per template)
```

## Gaps

1. **No slot model.** Fixtures store a/b entrants, not "Round 2 Slot 5". Pairings are worked out from the standings, not from a map.
2. **No result-time progression.** The next opponent appears only after the whole round is generated. SportyHQ fills each slot as soon as its feeding match is decided.
3. **No templates.** Your 12/14/18 examples have no machine-readable form, and there is nothing for 8–32 (including odd counts).
4. **Byes.** Today the lowest seed gets a bye each round, with no repeat rules. Templates must say which slot gets the bye in every round, and that no one gets a second bye before everyone has had one.
5. **Rematches.** Fixed maps can produce repeat opponents. SportyHQ accepts that. The current `swissRound` throws `swiss_repeat` instead. We need a policy for each template: allow, or swap within an allowed slot band.
6. **Round count.** The template fixes the number of rounds (normally ceil(log2 N), or a set number). This must be checked against `swissRounds` / `swissRoundsConfirmed` in the builder.
7. **Final ranking.** The final position should be the final slot, not points plus Buchholz. `position_swap` gets close, but it moves players in standings order, not by slot.
8. **Scheduling.** A partly known fixture (one slot filled) needs date, time and court, or a play-by date, before the opponent is known. Court holds or booking from fixtures must handle a fixture that is still "TBD v Player".
9. **Server guards** assume whole-round creation. The single-insert pattern would need a new guard, not a relaxed old one.

## Proposed architecture (new, opt-in, never alters existing draws)

- **New stage kind `swiss_positional`.** It sits beside `swiss`. Existing `swiss` stages, `position_swap`, Uitsig and live Riverside Club Champs are untouched. It is switched on only by a new Riverside flag `tournament_swiss_positional`.
- **Template library** in `src/lib/tournaments/swiss-positional/templates.ts`: pure data, keyed by entrant count 8–32. For each round and match it holds `[slotA, slotB] -> {winnerSlot, loserSlot}`, plus a bye slot and a rematch policy.
  - Your SportyHQ screenshots for 12/14/18 are encoded exactly, as golden fixtures.
  - Other counts are generated by a deterministic rule ("winner takes min slot, loser max slot; next round pairs adjacent slot blocks"). This needs your confirmation against SportyHQ for 2–3 sample sizes (e.g. 16, 24, 32).
  - Odd N: use a virtual slot N+1 = BYE. The bye holder advances as a winner. The template is checked so no one gets a second bye before everyone has had one.
- **Validator** (pure function, runs at draft and Final Setup): every slot is filled exactly once per round, maps are complete and each slot is used once, round count is correct, there are no orphan slots, the number of byes is reported, and repeat opponents are counted and shown in the preview.
- **Slot persistence.** Store `slot_a` / `slot_b` per fixture (or a `stage_slot` mapping) in beta-local state. Round r+1 fixtures are created up front as "Slot x v Slot y" placeholders. When a result is confirmed, a server function writes the winner and loser into their target slots in one atomic, idempotent step (keyed by fixture id). It refuses if the target fixture is already started or decided.
- **Result timing.** A slot is filled on confirmed results only. Correcting a result re-routes only downstream fixtures that have not started. If a downstream fixture has a result, the change is blocked and needs an impact preview.
- **Multiple divisions.** One template instance per division, picked automatically from that division's final entrant count when the draw is generated. Changing the count after the draw needs the running-tournament impact flow.
- **Ranking.** Final position = final slot after the last round, shown in `SwissProgressionView` (movement = slot change).
- **Scheduling.** Placeholder fixtures carry the stage rule (fixed date/time/court or play-by). Booking from a fixture stays locked until both slots are filled.

## Phased proposal

1. **Templates + validator (pure, tests only).** Encode the 12/14/18 screenshot maps and the generated rule for 8–32. Vitest golden tests: every round matches the screenshots, every template passes validation, bye fairness holds, and repeat-opponent counts are reported. You sign off on the generated maps for sizes without screenshots.
2. **Engine (pure).** `swiss_positional` round 1, slot routing on a result, final ranking, and integrity checks in `contract.ts`. No database changes.
3. **Beta-local persistence + server routing.** Slot columns and an atomic routing function with its own guard. The migration is limited to new nullable columns and a new function. Existing guards and rows are unchanged.
4. **Builder + UI (Riverside flag only).** A format choice in the builder, a template preview with an "opponent TBD" view, and a progression view by slot.
5. **Synthetic E2E in Riverside** with test entrants (8, 12, 14, 18, 24, 32, and odd counts). No real notices or bookings. Then sign-off and staged rollout.

## Safety

- Live Riverside Club Champs, Uitsig, existing `swiss` / `position_swap` stages and history are never migrated or recalculated.
- There is no change to the current server Swiss guards. The new kind has its own guard.
- Nothing is published, messaged or booked without explicit approval.
