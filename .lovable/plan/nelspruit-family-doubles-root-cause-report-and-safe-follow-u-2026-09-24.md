# Nelspruit Family Doubles — root-cause report and safe follow-up plan

## What the saved tournament intends
- One fixed-pair doubles division, single round robin in two six-pair pools, then **position play-offs**: Pool A #1 versus Pool B #1 for 1st/2nd, down to #6 versus #6 for 11th/12th. The saved settings enable play-offs and specify a 15-minute break; they do not specify rotating partners. The saved `league_playoff_qualifiers.1 = 2` does not affect **position** mode.
- Thirty pool fixtures are expected: fifteen in each pool, five games per pair. Six play-off finals are expected, one per finishing position. This is not a further round-robin round.

## What the current records show (read at investigation time)
- All **30/30** pool fixtures are completed. Each of the 12 pairs appears in exactly five pool games. There are six `playoff_final` fixtures, with three completed, one in progress and two scheduled. There are no additional `group` rounds after round 5, and no extra play-off rows in the current snapshot.
- Twelve entry rows match twelve confirmed doubles-pair records; no entry lacks its confirmed pair. All twelve play-off sides are distinct fixed pairs also present in the pools. No current player has two different partners in pool or play-off rows. Thus the reported partner switching is **not present in the latest snapshot**; it describes earlier fixture reshuffles, not evidence of a deliberate individual re-pairing rule.
- These are current-state observations, not a complete history of deleted/replaced fixtures. Earlier repairs and the possibility of disappearing duplicate rows are recorded in the conversation, but the current match table alone cannot reconstruct every prior version.

## Confirmed root cause and remaining exposure
1. The earlier standings calculation included `playoff_*` fixtures sharing the division number as though they were pool fixtures. This gave a phantom sixth/seventh pool appearance and changed the rankings used for seeding. The detail page automatically recalculated and rewrote **uncompleted** play-off participants after completed results, so that faulty input moved *whole doubles pairs* between finals. It could also insert/delete rows while matching placeholders; there is no unique index for play-off position slots. Evidence: `ClubChampsView.tsx` standings and `generatePlayoffs` logic; the 24 Sep issue-log entry and latest diff.
2. The saved draw is already a complete five-round round robin. There is **no evidence in current data of a sixth pool round being generated**. The additional game prompts were play-offs being counted/displayed in pool standings, plus unstable play-off assignments; do not interpret this as proven new round-robin fixture generation.
3. A recent code change filters standings to `stage = group` and stops **automatic** re-seeding once pools are complete *and* a play-off is underway. This addresses the main feedback loop for this event, but is not a full pair/fixture freeze. Automatic provisional seeding still runs before the last pool result; the visible **“Regenerate play-offs”** button remains enabled during play-offs and its handler can overwrite scheduled/in-progress sides, delete unmatched uncompleted rows and create additional rows. The writes are sequential client calls, not one atomic transaction. No stored stage-lock/immutable team ID or unique play-off slot constraint enforces this across clients. No regression test presently exercises the completed-pool/started-play-off lock.
4. The position-playoff builder receives a `StandingEntity` carrying both `memberId` and `partnerId` and writes them together (`tournament-playoffs.ts` `setSide`); it does **not** intentionally take individual rankings and form new partners. However, later-round SF/QF winner resolution in `ClubChampsView.tsx` patches only player IDs without partner IDs; this is an independent future-doubles risk for knockout-mode or larger-pool brackets. This particular two-pool position event uses only direct finals, so that path did not cause its observed reshuffles.
5. Rebuild: reopening the editor loads the saved format/pools and active entry pairs, excluding cancelled registrations. Schedule preview counts the current `scheduleGroups` pairs, not `expected_players`, for play-off reservation. But `Rebuild Schedule` still deletes/reinserts **all** fixtures after participant-based result/bookings reconciliation; it is not a safe way to advance a running tournament. Pair identity is reconstructed from current entries rather than a persistent qualified-team snapshot, and rebuild settings are first hydrated from the selected tournament record in the editor (with only manual-draw fields explicitly re-fetched). A stale editor session or concurrent change can therefore use outdated settings. The protection guard only preserves outcomes/bookings where corresponding participants remain in the new draw; it does not itself make active play-off brackets immutable.

## Current status and data repair
- The current database is internally consistent on fixture count and pair membership; **do not perform another automatic rebuild or bulk play-off repair** on a running event. Three play-offs already have results and one is being marked. Compare official Pool A/B standings and any disputed outcomes against the six currently saved finals with the organiser before proposing a specific correction. Historical deleted/changed line-ups cannot be proved solely from current match rows; consult audit/activity records and backups if a historical accounting is required. No data was changed in this investigation.

## Recommended safe fix and test plan (not performed)
1. Snapshot the tournament, entries/pairs, settings, fixtures/results and bookings; get organiser confirmation of any disputed pair or completed-result changes. Never silently clear a score or notify players.
2. Introduce a server-enforced transition that freezes each qualifying **pair as one unit** when pool play closes; resolve downstream winner/loser as the whole pair. Only an explicit, permission-checked, audited substitution may change a member. Make finalising/advancing idempotent and transactional, with a unique key for each play-off slot.
3. Stop client-side re-seeding once qualification is final or any play-off is booked/in progress/played; block manual regeneration and full rebuild for a live stage unless a separate controlled correction workflow can prove no results, bookings or progression are damaged. Refresh settings and active entrants at execution time; reject stale editor state rather than rebuild from it.
4. Add regression tests for two pools of six fixed pairs, five games each, no play-off result in pool standings, stable partners and unique slots across repeated/concurrent attempts, downstream QF/SF winner/loser pair propagation, substitution boundaries, and rebuild after withdrawal/settings changes (including stale-editor rejection). Verify in a non-production copy before considering narrowly scoped live repair.
