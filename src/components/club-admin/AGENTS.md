# Club Admin tournament builder rules

- Club Admin > Tournaments is the single tournament home: the Step-by-Step start section sits above the normal list (no separate Beta tile; `?tab=champs_beta` maps to `champs`); list "Manage" opens `StepTournamentManagement` when `tournaments.beta_lifecycle` is set (management record rebuilt from the server row if missing on the device), otherwise the existing setup (Diamond and legacy); why: one entry point without routing Beta tournaments into the legacy wizard.
- Step-by-Step Beta "Generate draw & fixtures" converts the tournament to the structured engine: pure bridge `src/lib/smart-builder/step-draw.ts` (reconciled active registrations → reciprocal pairs, plan proposal incl. round-robin matchups Within / Between subcategories (same parent only) / Custom pairings (reciprocal, never inferred; saved on `beta_lifecycle.format_plan` so any device reads them), cross sets as one `mapped` division per connected set with explicit league positions + `entryGroups`, club ranking-point seeding that blocks rather than falls back, several play-by deadlines as per-round `roundDates`, engine dry-run preview, pool preview built on `src/lib/tournaments/pools.ts` (tournament pool_allocation, moveToPool) saved as explicit `PlannedStage.poolMembers`) + DB `step_prepare_draw` then the existing `generateStructuredTournament` via `structured_commit`; division game/entry group numbers resolve via `divisionGroup`/`divisionEntryGroups`; why: one generator, pairs never split, unsupported rules stop instead of being substituted, results never lost.
- Step-by-Step Beta answers are stored per identity via `src/lib/smart-builder/step-storage.ts` (one unfinished new draft per club, one plan per created tournament; the old shared slot is migrated once), and a created tournament's full answers are mirrored to `tournaments.beta_lifecycle.answers` so Edit setup on a device without the plan loads them (fallback: format_plan + name/start date); the New tile never loads a tournament plan and never silently resumes a draft; why: a new setup must never inherit an existing tournament id, and editing must never open blank on another device.
- Knockout categories run on the paced engine `src/lib/tournaments/paced-knockout.ts`: Builder stores `koPace` (paced/immediate) and `koPairing` (progressive/traditional) on the format plan (missing = paced + progressive), editable on Generate draw beside "When games are played" and saved to `beta_lifecycle.format_plan.formatOverrides`; Generate draw creates only the paced Round 1 (`PlannedStage.paced`), and Manage Tournament's `StepKnockoutRoundsPanel` proposes/confirms one round at a time from the active field, pacing towards the milestone resolved from the existing Stages & scheduling choice (own category play-off stages win, else shared ones unless play-off dates are per category); knockout is never validated with round-robin round counts; why: no fixture may assume a winner and leagues must reach their play-off milestone on time.
- Pools are a partition, not a format: Knockout + "Create pools = Yes" stays `kind: "knockout"` with `pools > 1` (`isPooledKnockout`), each pool is eliminated down to its qualifiers (`poolKnockoutTarget`: explicit per-pool qualifiers, else milestone ÷ pools, else pool winner) via `paced.perPool` + `poolMembers` (rows carry `pool_number`, no pool table), then Manage's Knockout rounds panel runs the combined survivors to the milestone; only Swiss is blocked inside pools; why: knockout never inherits round-robin maths.
- Paced knockout Round 1 is reviewed in Generate draw before anything is created: the organiser's edited matches travel as `paced.pairs`/`paced.poolPairs` and the engine uses them exactly (refusing cross-pool, repeated or unknown players); why: fixtures must never be created from matchups the organiser hasn't seen.
- Knockout formal play-offs are optional: the first configured play-off stage (own, else shared) sets the pacing target and every path/qualification text via `paced-knockout.ts` (`milestoneFor`, `playoffSteps`, `configuredPathText`); removing a stage with played games is refused; why: Quarterfinals must never be implied when organisers start at Semifinals or Final.
- Cross-league matchups are canonical unordered group-pair edges built from every cross group's selection (`crossEdges` in `step-draw.ts`); one side selecting is enough, reciprocal selections never duplicate, a setup with no named groups defaults to all same-discipline cross groups, and `crossHow: "players"` creates only the organiser's de-duplicated `crossPlayerMatches` instead of the full cross product; why: one config source for UI, preview and generation.
- Step-by-Step scheduling preferences (rest, court allocation, per-category courts) live on `tournaments.beta_lifecycle.scheduling_prefs` and are applied only by `planTimedSchedule` (`formal-stage-schedule.ts` → pure `scheduling-prefs.ts`), which both the Generate page feasibility line and the real allocation call; default prefs run the previous planners unchanged and prefs apply only to wave-packed (Bells/waves) fixed stages; why: preview and generation must never disagree, and existing tournaments keep their behaviour.
