# Step-by-Step Beta builder rules
- Step-by-Step Beta match scoring is device-local, with tournament default and category/subcategory overrides resolved only for planning; why: guided choices must not alter live competition rules before creation is supported.
- Step-by-Step Beta planned competition format (pools/knockout/swiss/cross-league/later) is device-local and provisional with category/subcategory overrides; playoffs derive from it and a "Confirm final format" checkpoint is required before any generation; why: format must never be fixed before real entries are known.
- Step-by-Step Beta seeding plan and the Club Champs branch (basics, per-group expected entries, start date only (end = last planned stage), a single Stages & scheduling timeline holding the playoff synchronisation choice and per-stage play-by/scheduled plan, with the rounds-to-playoffs transition inferred from stage order) reuse the same answers object and shared steps, never a separate engine; seeds, stages and fixtures are only attached after the post-registration Final Format Review; why: one source of truth, and categories progress independently.
- Step-by-Step Beta accepted payment methods derive from the host club's Banking settings via `src/lib/smart-builder/payment-options.ts` (map 1:1 to `tournaments.payment_methods`), and its "Book courts now" writes idempotent `bookings` rows (`external_id` `sbs:<planId>:…`, clashes skipped) via `src/lib/smart-builder/stage-bookings.ts`; why: never offer a method the club can't accept, never double-book.
- Step-by-Step Beta handover: Summary's "Complete setup & continue" creates/updates the tournament via the `club_champs` insert (`src/lib/smart-builder/step-handover.ts`), enters admin-picked players as `club_champs_registrations` (never paid by selection), and stores lifecycle stage + deferred "Decide later" items device-local for `StepTournamentManagement`; why: no schema change while the Beta is on trial, and re-saving must never duplicate the tournament.
- Step-by-Step Beta WhatsApp group link is saved to the existing `tournament_whatsapp_groups` row (one per tournament, archived when removed); whether to include it in messages lives on `tournaments.beta_lifecycle.wa_include`; why: one source of truth for the group link, shared with the Current Builder.
- Step-by-Step Beta "After-match notifications" maps 1:1 onto the existing `tournaments.result_notify_scope/_channels` (queue_champ_result_emails trigger + dispatch-champ-result-messages); unpaid entries warn but never block finalising/draw, matching the existing engine; why: one result-message engine and no invented payment gate.
- Step-by-Step Beta "Must the fee be paid before the entry is confirmed?" maps onto the existing `payment_timing` (Yes = on_entry, No = after_acceptance); `payment_required` stays true whenever there is a fee so Pay remains available; Finalise readiness blocks on unpaid entries only when payment_timing = on_entry; why: reuse the existing field, never hide a real amount owed.
- Step-by-Step Beta "Generate draw & fixtures" converts the tournament to the structured engine: pure bridge `src/lib/smart-builder/step-draw.ts` (reconciled active registrations → reciprocal pairs, plan proposal incl. round-robin matchups Within / Between subcategories (same parent only) / Custom pairings (reciprocal, never inferred; saved on `beta_lifecycle.format_plan` so any device reads them), cross sets as one `mapped` division per connected set with explicit league positions + `entryGroups`, club ranking-point seeding that blocks rather than falls back, several play-by deadlines as per-round `roundDates`, engine dry-run preview, pool preview built on `src/lib/tournaments/pools.ts` (tournament pool_allocation, moveToPool) saved as explicit `PlannedStage.poolMembers`) + DB `step_prepare_draw` then the existing `generateStructuredTournament` via `structured_commit`; division game/entry group numbers resolve via `divisionGroup`/`divisionEntryGroups`; why: one generator, pairs never split, unsupported rules stop instead of being substituted, results never lost.
- Step-by-Step Beta templates: "My templates" are club-scoped `tournament_templates` rows (`template_key=step_by_step`, club admins only) holding a stripped `StepAnswers` copy via `src/lib/smart-builder/step-templates.ts`; pre-built templates are code-shipped (`PREBUILT_TEMPLATES`); why: templates must never carry players/payments/results and starting from one must never modify the master.
- Step-by-Step Beta Diamond League is offered only under Pre-built templates and opens the Current Builder's own Diamond setup (`ClubChampsTab launchDiamond` → `team_league_events` + `dl:` fixtures); the old Beta stage-model Diamond (`smart-builder/diamond-league.ts` template) is retired for creation and old drafts only show a retired note; why: one proven Diamond engine and one scalable entry for standard templates.
- Step-by-Step Beta play-offs: timeline play-off stages become real predefined `mapped` stages via `src/lib/smart-builder/playoff-chain.ts` (first stage from finishing positions by its pairing, every later stage from the previous stage's winners via mapping source `stage_winners`), "Start this stage" maps to `PlannedStage.waitForOrganiser`, planned sessions are booked through `self_schedule_champ_match` by `playoff-schedule.ts`, and setup contradictions go through `src/lib/smart-builder/consistency.ts` (blocks Complete setup and Generate draw); why: one progression engine, no impossible brackets, no silently ignored answers.
- Step-by-Step Beta answers are stored per identity via `src/lib/smart-builder/step-storage.ts` (one unfinished new draft per club, one plan per created tournament; the old shared slot is migrated once); the New tile never loads a tournament plan and never silently resumes a draft; why: a new setup must never inherit an existing tournament id.
- The tournament home shows only the three creation choices; created tournaments are managed solely from the normal Club Tournaments cards (Manage). Device-local handover/plan data is kept, never pruned from the landing page; why: one management route, and cleanup must never destroy live fixtures or history.
- Step-by-Step Beta run overview (`src/lib/smart-builder/run-overview.ts` + `StepRunOverview`) derives lifecycle (running/complete) and the next action per path from stored games via `stageLifecycle`, never from dates or a manual Activate click; qualifying ties surface as Action required; why: Riverside sat at "Activate" with all games played.
- Step-by-Step Beta pool creation belongs on the lowest configured grouping in Subcategories (`poolPlan`: none / auto with target / decide later); playoff qualification belongs in Playoffs or Club Champs Stages & scheduling (`playoffPoolQualifiers`, with legacy `poolPlan.perPool/runnersUp` read fallback). Real pools are proposed from actual entrants at Generate draw, "Decide later" blocks until accepted, and between-subcategory pool play blocks rather than guessing a mapping; why: pools subdivide a subcategory, never replace it, and qualification depends on the planned playoff field.
- Pool play is a hard boundary: the engine rejects any pool fixture pairing two pools or a pool count ≠ n·(n−1)/2 per leg (`src/lib/tournaments/pool-boundaries.ts`), Generate draw blocks unresolved/duplicated/missing pool places, and standings show one table per generated pool (from persisted `pool_number`); why: cross-pool meetings belong only to a configured play-off stage.
- Step-by-Step Beta play-off scheduling books games INTO the stage's own `sbs:` session reservation by carving each slot out of it (never treated as a clash). Court-slot order for centrally scheduled play-off stages comes from `src/lib/smart-builder/playoff-slot-order.ts` (linked `leagues.level`: lower level first, Ladies before Men within a level; organiser `schedule.slotOrder` overrides; missing/contradictory levels warn and keep draw order); why: scheduling must never guess or touch qualification, pairings or progression.
- Club Admin > Tournaments is the single tournament home: the Step-by-Step start section sits above the normal list (no separate Beta tile; `?tab=champs_beta` maps to `champs`); list "Manage" opens `StepTournamentManagement` when `tournaments.beta_lifecycle` is set (management record rebuilt from the server row if missing on the device), otherwise the existing setup (Diamond and legacy); why: one entry point without routing Beta tournaments into the legacy wizard.
- Knockout categories run on the paced engine `src/lib/tournaments/paced-knockout.ts`: Builder stores `koPace` (paced/immediate) and `koPairing` (progressive/traditional) on the format plan (missing = paced + progressive), editable on Generate draw beside "When games are played" and saved to `beta_lifecycle.format_plan.formatOverrides`; Generate draw creates only the paced Round 1 (`PlannedStage.paced`), and Manage Tournament's `StepKnockoutRoundsPanel` proposes/confirms one round at a time from the active field, pacing towards the milestone resolved from the existing Stages & scheduling choice (own category play-off stages win, else shared ones unless play-off dates are per category); knockout is never validated with round-robin round counts; why: no fixture may assume a winner and leagues must reach their play-off milestone on time.
- Pools are a partition, not a format: Knockout + "Create pools = Yes" stays `kind: "knockout"` with `pools > 1` (`isPooledKnockout`), each pool is eliminated down to its qualifiers (`poolKnockoutTarget`: explicit per-pool qualifiers, else milestone ÷ pools, else pool winner) via `paced.perPool` + `poolMembers` (rows carry `pool_number`, no pool table), then Manage's Knockout rounds panel runs the combined survivors to the milestone; only Swiss is blocked inside pools; why: knockout never inherits round-robin maths.
- Paced knockout Round 1 is reviewed in Generate draw before anything is created: the organiser's edited matches travel as `paced.pairs`/`paced.poolPairs` and the engine uses them exactly (refusing cross-pool, repeated or unknown players); why: fixtures must never be created from matchups the organiser hasn't seen.
- Standings "What's next · Knockout rounds" (`KnockoutNextActions`, admins only) reads `koDivisionActions` from `StepKnockoutRoundsPanel` (same `computeKoUnit` state machine) and only deep-links to Manage via `/club-admin?tab=champs&manage=<id>&ko=<group>`; why: one approval UI, and the shortcut can never disagree with Manage.
- Knockout formal play-offs are optional: the first configured play-off stage (own, else shared) sets the pacing target and every path/qualification text via `paced-knockout.ts` (`milestoneFor`, `playoffSteps`, `configuredPathText`); removing a stage with played games is refused; why: Quarterfinals must never be implied when organisers start at Semifinals or Final.

- Any round/stage with a fixed date + time window + selected courts is slotted only by `src/lib/tournaments/formal-stage-schedule.ts` (last configured category first, capacity shortfall blocks); every fixture creation path calls it; why: fixed stages must never produce TBD/player-booked games.
- Cross-league matchups are canonical unordered group-pair edges built from every cross group's selection (`crossEdges` in `step-draw.ts`); one side selecting is enough, reciprocal selections never duplicate, a setup with no named groups defaults to all same-discipline cross groups, and `crossHow: "players"` creates only the organiser's de-duplicated `crossPlayerMatches` instead of the full cross product; why: one config source for UI, preview and generation.
- Step-by-Step scheduling preferences (rest, court allocation, per-category courts) live on `tournaments.beta_lifecycle.scheduling_prefs` and are applied only by `planTimedSchedule` (`formal-stage-schedule.ts` → pure `scheduling-prefs.ts`), which both the Generate page feasibility line and the real allocation call; default prefs run the previous planners unchanged and prefs apply only to wave-packed (Bells/waves) fixed stages; why: preview and generation must never disagree, and existing tournaments keep their behaviour.
- Standings championship outcome/awards live on `tournaments.beta_lifecycle.standings_awards` via `src/lib/tournaments/standings-outcome.ts` (absent = existing behaviour; winner source stays the progression config; Wooden Spoon only when complete); why: never assume every tournament crowns an individual.
- Step-by-Step "Match scoring" (incl. per-category overrides) is copied onto the live per-division `league_scoring_modes/_points_per_game/_best_of/_win_conditions` by `divisionScoringColumns` in step-handover.ts on Complete setup; why: result entry read only those columns, so Bells setups were scored as standard best-of-5.
- The tournament page groups manager-only controls in one "Tournament Administration" card (canManage only); its Standings & awards reuses `StandingsAwardsSection`, which reads/writes `tournaments.beta_lifecycle.standings_awards` directly; why: Setup and the tournament page must share one saved standings config, never a copy.
- Weekend "Assign courts & times" drafts the timetable from Courts & Dates only (`format_plan.days`, `format_plan.scheduling` slot estimates, `format_plan.courtRules`) via `src/lib/tournaments/assumed-schedule.ts`; all-or-nothing, played/booked games never move, rest relaxed only when nothing else fits and reported; missing settings deep-link to `/club-admin?tab=champs&setup=<id>&step=Courts`; why: one source of truth for courts/dates and the scheduler never silently produces an invalid schedule.
- Weekend "Assign courts & times" (`src/lib/tournaments/assumed-schedule.ts`) plans the whole tournament in one run: qualifying games, existing TBD knockout/play-off rows, and planned play-offs without rows yet (`provisional-playoffs.ts`, labels from the configured per-stage pairing) held as idempotent `sbs:<champId>:po:<unit>|<QF|SF|Final|place>|<n>` court reservations that real play-off rows adopt in bracket order via `adoptProvisionalSlots` (called from `schedulePlannedPlayoffGames`); pacing and playoff start live on `format_plan.scheduling`; Standard games use Courts & Dates estimates, Bells games their own slot; why: play-off courts must be reserved before qualifying fills capacity, and capacity shortfalls must warn, never drop games.
- The fixed-date timed planner (`formal-stage-schedule.ts`) resolves play format via `resolveTimedFormat` from plan scoring (category/subcategory override → default); `tournament_rules.scoring_mode` is only a legacy fallback when the plan has no scoring, and no format forces a whole round to start together; why: Bells lockstep and stale Bells mode leaked into Standard tournaments.
- Whole-weekend tournaments (Courts & Dates scheduling, no stage timeline) turn the Playoffs answer into real predefined play-off stages (pairing only from the answer, else Define later); Generate/Rebuild then adds provisional TBD fixtures via `src/lib/smart-builder/playoff-placeholders.ts` (stage_key `<stage>#ph`, placeholder_a/b from the stage mapping) which Assign courts & times schedules, and `adoptPlaceholderRows` hands each slot to the real stage game then deletes the placeholder; why: the full structure must be visible and hold court time before qualifiers are known, without duplicates or engine changes.
- Step-by-Step "Pick players" stores `picks[memberId]` as a list of event keys (legacy single string read via `placesOf` in `src/lib/smart-builder/pick-entries.ts`); handover sends one item per (person, event) and DB `step_sync_admin_entrants` folds them into ONE registration with `division_choices` + per-event partner `club_champs_registrations.division_partners` (read via `registration_partner_for` / `partnerIn`, legacy fallback `partner_member_id`); `step_prepare_draw` checks duplicates and pairs per event; why: one person may enter several events with different partners without duplicating the person.

- Weekend play-offs are globally gated: the first play-off stage of every event starts only after ALL qualifying games of the tournament (every category) end plus the configured gap, or the fixed start if later (a fixed start earlier than qualifying is reported as a conflict); play-off fixture headings always lead with the event name via `playoffHeadingText`; why: playoffs were scheduled before other categories' qualifying finished and '#1 vs #4' rows were ambiguous.
- Step-by-Step invite mode sends real invitations via `src/lib/smart-builder/step-invite.ts` + `StepInvitePanel`: audience (all club / clubs / league teams / individuals) resolves through the shared fail-closed `resolveInviteAudience`, rows are planned by `planInviteRows` (declined/cancelled re-open, confirmed entries never touched), and sends go through the Comms engine with per-recipient entry links; why: one audience engine, and a selected send can never widen beyond the picked audience.
