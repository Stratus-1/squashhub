# Step-by-Step Beta builder rules
- Doubles serving selection is shared by Standard and Bells categories in the original structure screen, retaining category locks and the existing marker method; why: scoring mode must not hide serving rules.
- Eligibility audience toggles preserve other selected audiences and retained league IDs when leagues are deselected; why: removing automatic league placement must not remove manual picks or widen a manual-only audience.
- Step-by-Step Beta match scoring is device-local, with tournament default and category/subcategory overrides resolved only for planning; why: guided choices must not alter live competition rules before creation is supported.
- Step-by-Step Beta planned competition format (pools/knockout/swiss/cross-league/later) is device-local and provisional with category/subcategory overrides; playoffs derive from it and a "Confirm final format" checkpoint is required before any generation; why: format must never be fixed before real entries are known.
- Step-by-Step Beta seeding plan and the Club Champs branch (basics, per-group expected entries, start date only (end = last planned stage), a single Stages & scheduling timeline holding the playoff synchronisation choice and per-stage play-by/scheduled plan, with the rounds-to-playoffs transition inferred from stage order) reuse the same answers object and shared steps, never a separate engine; seeds, stages and fixtures are only attached after the post-registration Final Format Review; why: one source of truth, and categories progress independently.
- The tournament home shows only the three creation choices; created tournaments are managed solely from the normal Club Tournaments cards (Manage). Device-local handover/plan data is kept, never pruned from the landing page; why: one management route, and cleanup must never destroy live fixtures or history.
- The tournament page groups manager-only controls in one "Tournament Administration" card (canManage only); its Standings & awards reuses `StandingsAwardsSection`, which reads/writes `tournaments.beta_lifecycle.standings_awards` directly; why: Setup and the tournament page must share one saved standings config, never a copy.
- Standings "What's next · Knockout rounds" (`KnockoutNextActions`, admins only) reads `koDivisionActions` from `StepKnockoutRoundsPanel` (same `computeKoUnit` state machine) and only deep-links to Manage via `/club-admin?tab=champs&manage=<id>&ko=<group>`; why: one approval UI, and the shortcut can never disagree with Manage.
- Beta builder management cards are device-local projections verified against club-scoped tournament rows, and card removal never deletes a real tournament; why: a stale local record must not survive deletion or erase competition history.
- Swiss round count is per category: with club switch `tournament_swiss_category_rounds` the builder writes `club_champs.swiss_rounds` keyed by game group and setup lookups use the stable unit key (then parent), never a name prefix; switch off keeps legacy behaviour; why: one category must never overwrite another and live tournaments stay unchanged.
- The old Riverside row/canvas flags are retired. The independent card-structure gate consolidates What/Match/Categories/Guide/Subcategories/Overrides/Format in Riverside new drafts on all hosts with explicit local save and separate table-only Structure review; scheduling and Dates/Courts remain separate, creation blocked; why: live planning tests use one answers store without existing-tournament writes or discarded canvas revival.
- Original alternate-builder structure is reused through ClubChampsTab's structureOnly mode with original-structure.ts adapters; the complete original snapshot remains in StepAnswers.originalStructure and unsupported original settings are not applied downstream; why: preserve the original questions and one local save authority while creation remains blocked.
- The one-page card-structure builder is the only structure flow for every club (`cardStructurePilot` always true; old multi-page structure steps retired); why: one builder, no per-club divergence.
- Tournament administration hierarchy uses explicit local roots and light-only semantic surfaces, including notification portals; why: public/member pages and existing dark mode must remain unchanged.
- Draw notification dialogs keep the header and actions outside one viewport-bounded scrolling body; why: expanded personalized previews must not hide send/cancel controls or scroll the underlying page.
- The Structure screen's per-category Swiss stage plan is the single source of the Swiss round count; it is copied into builder_spec on save and never lowered below a round with games; why: the progression log and engine read builder_spec.
- Riverside RR-finish controls live below Category seeding in the reachable original structure screen and round-trip through the original-structure adapter into stagePlans and the draw spec; why: CardStructureEditor's club-backed early return bypasses its legacy card markup.
- Play-offs step selects only whether there are play-offs and how many stages (QF/SF/F); pairing and qualification are chosen only in Stages & scheduling, for all clubs. Old saved playoff style/pairing values are read for legacy display only; why: two editable settings disagreed (Men's A placement vs crossover).
- Step-by-Step Beta "Include visitors" (Who may enter) is one tournament-level opt-in (`StepAnswers.includeVisitors`): the pick list loads ALL active `role='visitor'` member rows of the club (manual visitors added in Club Admin count too — a visitor needs no registered user), and club sign-in visitors are additionally promoted to idempotent `visitor:<id>` member rows via `src/lib/tournaments/visitor-promotion.ts` (phone copied, never billed); it also feeds the invitation audience (`resolveInviteAudience(includeVisitors)`); default off and visitors are never invited without it; why: one opt-in, one promotion path, and invites must never silently include or exclude visitors.
