# Step-by-Step Beta builder rules
- Step-by-Step Beta match scoring is device-local, with tournament default and category/subcategory overrides resolved only for planning; why: guided choices must not alter live competition rules before creation is supported.
- Step-by-Step Beta planned competition format (pools/knockout/swiss/cross-league/later) is device-local and provisional with category/subcategory overrides; playoffs derive from it and a "Confirm final format" checkpoint is required before any generation; why: format must never be fixed before real entries are known.
- Step-by-Step Beta seeding plan and the Club Champs branch (basics, per-group expected entries, start date only (end = last planned stage), a single Stages & scheduling timeline holding the playoff synchronisation choice and per-stage play-by/scheduled plan, with the rounds-to-playoffs transition inferred from stage order) reuse the same answers object and shared steps, never a separate engine; seeds, stages and fixtures are only attached after the post-registration Final Format Review; why: one source of truth, and categories progress independently.
- Step-by-Step Beta accepted payment methods derive from the host club's Banking settings via `src/lib/smart-builder/payment-options.ts` (map 1:1 to `tournaments.payment_methods`), and its "Book courts now" writes idempotent `bookings` rows (`external_id` `sbs:<planId>:…`, clashes skipped) via `src/lib/smart-builder/stage-bookings.ts`; why: never offer a method the club can't accept, never double-book.
- Step-by-Step Beta handover: Summary's "Complete setup & continue" creates/updates the tournament via the `club_champs` insert (`src/lib/smart-builder/step-handover.ts`), enters admin-picked players as `club_champs_registrations` (never paid by selection), and stores lifecycle stage + deferred "Decide later" items device-local for `StepTournamentManagement`; why: no schema change while the Beta is on trial, and re-saving must never duplicate the tournament.
- Step-by-Step Beta WhatsApp group link is saved to the existing `tournament_whatsapp_groups` row (one per tournament, archived when removed); whether to include it in messages lives on `tournaments.beta_lifecycle.wa_include`; why: one source of truth for the group link, shared with the Current Builder.
- Step-by-Step Beta "After-match notifications" maps 1:1 onto the existing `tournaments.result_notify_scope/_channels` (queue_champ_result_emails trigger + dispatch-champ-result-messages); unpaid entries warn but never block finalising/draw, matching the existing engine; why: one result-message engine and no invented payment gate.
- Step-by-Step Beta "Must the fee be paid before the entry is confirmed?" maps onto the existing `payment_timing` (Yes = on_entry, No = after_acceptance); `payment_required` stays true whenever there is a fee so Pay remains available; Finalise readiness blocks on unpaid entries only when payment_timing = on_entry; why: reuse the existing field, never hide a real amount owed.
- Step-by-Step Beta "Generate draw & fixtures" converts the tournament to the structured engine: pure bridge `src/lib/smart-builder/step-draw.ts` (reconciled active registrations → reciprocal pairs, plan proposal incl. round-robin matchups Within / Between subcategories (same parent only) / Custom pairings (reciprocal, never inferred; saved on `beta_lifecycle.format_plan` so any device reads them), cross sets as one `mapped` division per connected set with explicit league positions + `entryGroups`, club ranking-point seeding that blocks rather than falls back, several play-by deadlines as per-round `roundDates`, engine dry-run preview, pool preview built on `src/lib/tournaments/pools.ts` (tournament pool_allocation, moveToPool) saved as explicit `PlannedStage.poolMembers`) + DB `step_prepare_draw` then the existing `generateStructuredTournament` via `structured_commit`; division game/entry group numbers resolve via `divisionGroup`/`divisionEntryGroups`; why: one generator, pairs never split, unsupported rules stop instead of being substituted, results never lost.
- Step-by-Step Beta templates: "My templates" are club-scoped `tournament_templates` rows (`template_key=step_by_step`, club admins only) holding a stripped `StepAnswers` copy via `src/lib/smart-builder/step-templates.ts`; pre-built templates are code-shipped (`PREBUILT_TEMPLATES`) and Diamond League opens as a new draft in the existing Beta format editor; why: templates must never carry players/payments/results and starting from one must never modify the master.
- Step-by-Step Beta play-offs: timeline play-off stages become real predefined `mapped` stages via `src/lib/smart-builder/playoff-chain.ts` (first stage from finishing positions by its pairing, every later stage from the previous stage's winners via mapping source `stage_winners`), "Start this stage" maps to `PlannedStage.waitForOrganiser`, planned sessions are booked through `self_schedule_champ_match` by `playoff-schedule.ts`, and setup contradictions go through `src/lib/smart-builder/consistency.ts` (blocks Complete setup and Generate draw); why: one progression engine, no impossible brackets, no silently ignored answers.
- Step-by-Step Beta answers are stored per identity via `src/lib/smart-builder/step-storage.ts` (one unfinished new draft per club, one plan per created tournament; the old shared slot is migrated once); the New tile never loads a tournament plan and never silently resumes a draft; why: a new setup must never inherit an existing tournament id.
- Step-by-Step Beta run overview (`src/lib/smart-builder/run-overview.ts` + `StepRunOverview`) derives lifecycle (running/complete) and the next action per path from stored games via `stageLifecycle`, never from dates or a manual Activate click; qualifying ties surface as Action required; why: Riverside sat at "Activate" with all games played.
- Step-by-Step Beta pool creation belongs on the lowest configured grouping in Subcategories (`poolPlan`: none / auto with target / decide later); playoff qualification belongs in Playoffs or Club Champs Stages & scheduling (`playoffPoolQualifiers`, with legacy `poolPlan.perPool/runnersUp` read fallback). Real pools are proposed from actual entrants at Generate draw, "Decide later" blocks until accepted, and between-subcategory pool play blocks rather than guessing a mapping; why: pools subdivide a subcategory, never replace it, and qualification depends on the planned playoff field.
- Pool play is a hard boundary: the engine rejects any pool fixture pairing two pools or a pool count ≠ n·(n−1)/2 per leg (`src/lib/tournaments/pool-boundaries.ts`), Generate draw blocks unresolved/duplicated/missing pool places, and standings show one table per generated pool (from persisted `pool_number`); why: cross-pool meetings belong only to a configured play-off stage.
