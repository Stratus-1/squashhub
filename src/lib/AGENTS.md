# Domain rules (src/lib and related)

- Ladder refinement preserves unsaved sibling proposals and displays the category used to sort; why: saves must be repeatable and evidence truthful.
- Sessions (date/court/time blocks) are separate from stages: a stage joins an earlier stage's session only via explicit `Stage.sameSessionAs`; `sessionPlan` adds sequential durations; compound ties stay `Stage.tieFormat` rubbers; why: several stages can share one evening without being flagged as overlapping.
- Pool-v-pool league stages keep pool rotation (`legs`) and in-tie pairing (`tieFormat.pairing`: position/crossover/custom) as separate fields, one discipline per stage; rules live in `src/lib/smart-builder/ties.ts`; why: pairing must never be inferred from 'round robin'.
- Match scoring resolves tournament → stage (`Stage.scoring`) → round (`Stage.roundScoring`) in `src/lib/smart-builder/scoring.ts`; a Bells cap drives schedule minutes and missing caps block Create; why: stages in one session can use different scoring.
- Standings method per stage (`Stage.standings`: method, result points, combined, Bells score rule, ordered tie-breaks) lives in `src/lib/smart-builder/standings.ts`; required for pool-v-pool/Bells stages or once chosen, legacy round robins only warn; why: never invent ranking rules.
- Stage courts resolve pool home courts → `Division.courtKeys` → stage/default courts → tournament court pool, and match length from tie games/Bells cap/match minutes, in `src/lib/smart-builder/court-allocation.ts`; Diamond League shape scales via `diamondShape(capacity, poolSize, poolsPerDivision)`; why: courts belong to divisions/pools, entries vary.
- Engine capability lives in `src/lib/smart-builder/engine-support.ts` and is read by validate, Review, to-existing and specFromDefinition; unsupported stages block at design time; why: the builder must never design what the engine can't run.
- Pool-v-pool stages run as engine kind `mapped` with an explicit `StageMapping` (source → units/pairs → matchups by slot A1/B2) in `src/lib/tournaments/mapping.ts`; builder proposes it in `smart-builder/matchups.ts`, admin edits persist on `Stage.mapping`; why: who-plays-whom is data, never inferred from a 'cross-pool' label.
- Later play-off stages may be marked `Stage.defineLater` ("Define later"): `src/lib/smart-builder/deferred.ts` strips them from validation, schedule maths, engine support, the existing-model mapping and the Create spec (kept as `SpecDivision.deferredStages` planning targets only); why: a deliberately deferred semi-final/final must never block creating or running the stages that play now, and can never be advanced into before it is configured.
- Stage lifecycle (waiting/ready/blocked/active/completed/deferred/needs_setup) and automatic progression live in `src/lib/tournaments/progression.ts`; predefined stages start via the same engine calls after a dry run, Define-later stages are set up on the live tournament via `setupDeferredStage` (append-only `set_spec` commit op), tie orders go in `TournamentSpec.positionOrders`, and the DB trigger `guard_structured_stage_round_once` refuses a second copy of a stage round; why: progression must never guess, never disturb earlier stages, and never double-generate.
- Every self-registration path must call `useDuplicateGuard` (backend `account-recovery`, logic in `supabase/functions/_shared/person-match.ts`) before creating a person; why: one national person record, and existing emails are revealed only after phone OTP.
- Doubles original pairs are dated rows in league_team_pairs (effective_from/effective_to); edits close+insert, never overwrite; why: bonus and history must follow the pair official on each fixture date.
- Bar/shop inventory: stock lives only on `bar_items.item_kind='stock'` rows in `stock_units` (smallest unit, e.g. tots; `unit_yield` per bottle) and changes only via `bar_stock_apply` with a `bar_stock_movements` row; Single/Double are `option` rows and combos are `special` rows (+ `bar_special_components`) holding no stock; divisions/categories are per-club rows with archive, never hard-delete in-use ones; why: one inventory engine for every club, exact open-bottle stock, atomic combo deduction and an audit trail.
- Bar stock costing is optional per club (`club_bar_settings.costing_enabled`); `bar_items.avg_unit_cost` is per smallest unit, re-averaged only by purchases inside `bar_stock_apply`, corrected only via audited `bar_set_average_cost`; every movement snapshots `unit_cost`/`cost_value` and reports read snapshots (`bar_cost_of_sales`); why: historic COGS must never change and clubs without costing stay untouched.
- Bar item bulk import: parsing/validation/matching is pure in `src/lib/bar-import.ts` (club-scoped matching by name+variant or barcode, specials rejected, existing stock never changed — stocktake only); `ImportItemsDialog` writes only after explicit confirm; why: imports must never create duplicates, phantom stock or cross-club changes.
- Bar item kind `made_to_order` (Restaurant category food like burgers): holds no stock, always on the menu (`onMenu` skips the stock check, QR menu lists it at zero stock), and `bar_consume_sale` deducts nothing; why: food is prepared to order, never stocked.
- Doubles serving is a pure state machine in `src/lib/marker/doubles-serving.ts` (methods even_odd/by_position/second_server; even_odd side = combined score of both pairs, even → right); the method lives on `league_rules.doubles_serving_method` and `tournaments.doubles_serving_method` / `league_doubles_serving_methods` (null = manual legacy serving), and the marker persists positions + server state with its local session; why: the marker must know the real server per pair and singles must stay untouched.
- Diamond League is a normal-wizard team mode: `team_league_events` links 1:1 by `tournament_id`; `autoSlotPlayers` preserves locks; `buildPoolWeeks` drives preview, saved weeks and stable `dl:` match rows; why: invitations, courts, Upcoming, marking and standings must share one tournament fixture identity. Per-division schedules live on `config.divisionSchedules[pool]` (play days/start date/start time → per-tie `date`/`time`, courts restart per own night; missing = shared weekly dates) , optional `config.firstWeekPairs[pool]` relabels the round robin so week 1 matches the organiser (later weeks derived, invalid plans fall back to default), and `config.playoffs === false` stops semis/finals; why: divisions may play different nights without breaking legacy events.
- Diamond League doubles pairs are re-seeded by DB trigger `diamond_seed_doubles_from_singles` once a tie's singles are all scored (points scored, level -> higher position); why: pairing is automatic and never touches started doubles.

- Club Google registration uses a public same-origin callback with club context and reuses existing club_members identity; only a unique exact-email unclaimed match auto-claims; why: preserve member history without guessing across shared family emails.

- Tournament round dates come from `src/lib/tournaments/round-plan.ts`: setup asks only for opening rounds the pools need and the play-off rounds the play-off type has; play-off games are dated only by their play-off round (`playoffDeadline`), never a pool round; why: play-offs borrowed Round 1's date.
- Per-stage scheduling (pools vs each play-off round: play-by date or fixed date & courts) is stored as `milestone_play_by.stage_scheduling` and resolved by `stageModeForGame`/`playoffModeFor` in `round-plan.ts`, falling back to `scheduling_mode`; why: `club_champs` is a view with INSTEAD OF triggers, and owners mix play-by pools with booked finals.
- Step-by-Step Beta lifecycle stage lives in `tournaments.beta_lifecycle` (localStorage is only a cache) and all Beta player messaging goes through `comms_campaigns` + `send-comms-campaign` with per-recipient `member_vars`; why: 'informed' must reflect real, logged, retry-safe deliveries on any device.
- Step-by-Step organiser-entered players are synced as a set by DB `step_sync_admin_entrants` (add / update partner+category / withdraw unpicked, reversing an unpaid entry fee with an audited journal); "Add to my account" sets `club_champs_registrations.fee_settled_via='account'` → `fee_status='on_account'` (satisfied for readiness, never "paid"); why: replacements must be one-for-one and account charges are debts, not receipts.
- Tournament entry fee "settled" means paid, waived OR `on_account` (`champ_member_fee_settled`); every payment route (Stitch start, invite payment context, account charge, pair payment) checks it first, and a partner's fee charged to account moves the debt to the payer via `step_charge_pair_to_account` (partner's own charge reversed with audit); why: one authoritative settlement status, never a second charge or the wrong member's account.
- Tournament bookable courts resolve in DB `tournament_bookable_court_ids` (stage override courts/venue → explicit venue courts → legacy court_ids → host clubs' normal courts), mirrored in `src/lib/tournaments/bookable-courts.ts`; club events default to the owning club, regional/national need an explicit host club; the booking window and the match-court guard both read it; why: owner is never venue and the UI must never offer a court the backend rejects.
- Fixed-date round-robin/cross-league rounds (incl. Bells) are timed by `scheduleTimedRounds`/`planTimedRounds` in `src/lib/tournaments/formal-stage-schedule.ts`: each round starts together at its bell (slot = match_duration_minutes + buffer) on the plan day's own courts, next round one slot later, all-or-nothing on capacity (waves only when `format_plan.waves`); why: fixed Bells evenings need real times/courts, never TBD overflow.

- Tournament entry fee is charged per event: DB `champ_reg_own_due_cents` = event fee x events the player pays for themselves (no choices = 1 legacy event); a partner's cover is per event (`club_champs_registrations.covered_events` or a pay-for-partner `champ_doubles_pairs` row) and pairs confirm via `champ_member_event_paid`; unpaid fee amounts change only through audited `_champ_fee_adjust`, paid fees never change (extra events add an 'additional events' fee); client mirror in `src/lib/tournaments/entry-fee.ts`; why: multi-event entries must owe one fee per event and paying for a partner covers only the shared doubles event.

- League scorecards: an unstarted fixture shows the current team roster unless a side is flagged `*_lineup_explicit = true`; started/locked rubbers never change; why: roster edits must reach upcoming games without rewriting reserves or history.
- Match Day Access is an authorisation alternative, not a second UI: one persistent token per competition in `match_day_access` (court/match = URL suffix); `/md/*` renders the existing League Games screens inside `MatchDayDeviceContext`, sending REST requests as anon + `x-match-day-token` (`src/lib/match-day/device.ts`), and anon `md_hdr_*` RLS policies scope reads/writes to that season's open fixtures (names-only member columns, submit only with both captain signatures), audited as 'Match Day Access'; tournament links render the same Tournaments / ClubChampsView / MatchMarker / TournamentMatchLive screens (paths mapped by `useMdNavigate`, the RLS-bypassing `club_champs` view swapped for the filtered `md_club_champs`, score-only update guard trigger, `save_marker_match_result` device branch); why: one scoring engine, no admin/member exposure, tokens never minted per email.

- A new-member application is complete only once its signup steps saved a fee category (`src/lib/membership-application.ts`), never because a member number exists; why: clubs may auto-number applicants at account creation.
- Unfinished self-application progress lives server-side in `club_members.application_progress` (owner-only via `get_/save_my_application_progress` RPCs, no client column grant), cleared on completion; category, fees and admin alerts are written only by the final save; why: applicants resume on any device without being charged or approved early.
- A person may hold memberships at several clubs; joining a second club is a genuine new application created only via `apply_to_club_as_existing_person` after an explicit warning/confirm in `NoClubAccess`, reusing `person_id`; why: one national person record, and second-club joiners must never take the preloaded-activation shortcut or skip fees/approval.
- Step-by-Step Beta 'Import players' matching lives in `src/lib/smart-builder/pick-import.ts` (name required unless email+cell both match; event columns exclude league-history columns) and only ticks existing members into device-local picks; why: shared family emails must never pick the wrong person and imports never create people.

- Team standings derive from season-scoped fixtures + submitted/confirmed results via `src/lib/leagues/team-standings.ts`; rounds only label groups; why: a missing or unlinked round must never hide valid results.

- Diamond fixtures use `tournamentMatchDays` in `schedule-order.ts` for date headings and time/court order, never generated rounds; why: division weeks span different nights. Display only; saved fixtures unchanged.
- Knockout stages after the first play-off use fixed feeder paths (stage_winners by bracket_position); never reseed from standings — keeps brackets deterministic and auditable.
- Draw/round generation never dispatches player messages: `notifyRoundDraw` only sends when called with `skipPrompt: true` from an explicit organiser send (Send draw to players / future Manage Tournament → Notifications); why: test and regenerated draws must never reach players.
- Bar/Shop member-account debit limits: `club_bar_settings.bar_allow_member_debit`/`shop_allow_member_debit` (default true) are enforced by the statement trigger `bar_tab_enforce_member_debit` using `member_account_gate`, the SQL mirror of the court-booking `computeBookingGate` with no float, on the balance after the purchase; why: one arrears rule for bookings and POS, every charge path covered, refusals roll back stock and journals. Early basket warnings use `bar_account_charge_preview` (own member, bar staff or bar admins only), computed client-side with `previewBasketCharge`, fail open, and never replace the trigger; why: preview must not leak other members' balances.
- Scan-to-pay member-account charges have two verification paths: signed-in members confirmed at the scanned club charge directly via session-authorized RPCs (server re-checks membership ownership, entries marked verification_method 'session'), including atomic tip settlement wrappers; everyone else uses `bar_qr_lookup_member` + one-time code; why: app login is sufficient for self-charges, tips must never force OTP, and QR-only users must still prove identity.
- Member payment approval goes only through `finance_decide_member_transaction` (club-scoped finance permission, row lock, pending-only, audit row); why: Treasurers can approve without admin rights and a payment can never be posted twice.
- League team penalties are rows in `league_team_penalties` (positive points, reversal-stamped, never deleted) written only via admin RPCs and subtracted from season standings totals in `src/lib/leagues/team-penalties.ts`; why: penalties must never alter fixture scores, rubbers or bonus rules and must stay auditable.
- Swiss standings (page) and Swiss next-round pairing share one ranking, `swissTable` in `src/lib/tournaments/swiss-standings.ts` (match wins; bye = win with no Buchholz credit; Buchholz → Sonneborn-Berger default, configurable `Stage.tieBreaks`; original seed last). Swiss is detected per structured stage, never from legacy `scoring_mode`; why: the table must never show an order the pairing does not use.
- Swiss rounds are created one at a time via `swissRoundGate` (`src/lib/tournaments/swiss-round-gate.ts`): draw makes Round 1 only, Round N+1 only on admin confirm after every real Round N fixture is final (byes/voids final), never skip or exceed `swissRounds`; enforced server-side by DB trigger `guard_swiss_round_progression`; why: pairings must use confirmed results and buttons alone are not security.
- Tournament registration status honours `payment_timing`: with pay-before-entry off, payment never gates entry and is reported only via `fee_status`; why: unpaid entrants must still count and be draw-eligible.
- Tournament entry-fee basis lives on `tournaments.entry_fee_basis` (per_player/per_category; NULL = Needs confirmation, never back-filled) + `entry_fee_mixed_rule`; amounts come only from `src/lib/tournaments/entry-fees.ts` / DB `champ_registration_fee_lines`; every payment route first charges the fee via idempotent `ensure_tournament_entry_fee` (claim submit, claim approve, card settlement) and the payment then settles that one charge (bulk `champ_fee_post_charges` deprecated, no UI); member "already paid" reports are `champ_payment_claims` settled only by admin `champ_payment_claim_review` (excess → member credit topup); why: never guess a fee basis, double-charge, or mark paid without verification.
- Opponent contact sharing is ONE opt-in national preference per person (`person_contact_sharing`, never pre-ticked or implied by activating/entering) read only through SECURITY DEFINER RPCs: `get_fixture_opponent_contacts` (signed-in participant, one open fixture, rate-limited, logged) and service-only `fixture_opponent_contacts_for_member` used by `send-comms-campaign` at send time; under-18s share only a confirmed guardian contact and numbers vanish once a result/cancel exists; why: POPIA consent must be current per opponent and public/bulk paths must never see numbers.
- Tournament games split into Upcoming vs Results only via `src/lib/tournaments/fixture-split.ts` (byes/cancelled/walkovers → Results), used by every ClubChampsView layout incl. the public QR view; why: one game must never appear in both lists or differ between app and QR.

- Fixed-position Swiss full draws live only in `swiss_positional_pilot_draws` (pure engine `src/lib/tournaments/swiss-positional-draw.ts`, generated once, fixtures frozen by trigger, results via `swiss_pilot_record_result`), gated by `tournament_swiss_positional_draw`; why: the pilot must never write to live club_champs_matches, rankings or bookings until sign-off.
- Bar orders (`bar_orders`/lines/events) track fulfilment only; sales/stock are written once at submission via RPC and delivery never charges again; why: no double charging.
- Timed tournament scheduling places each round only on configured nights inside the 7 days ending on that round's play-by date (one round per week, shared by every category); a round with no night in its week writes nothing; why: rounds must never be packed into an earlier round's week.
- Structured-tournament stage auto-progression also runs server-side: a result trigger on club_champs_matches calls `auto-progress-tournaments`, which runs the same engine bundled from src via `bun scripts/build-auto-progress.ts` (rebuild after engine changes), staged by its ROLLOUT_CLUBS list, never sends notifications; why: next rounds must appear without an admin opening the page.
- Results-decided Swiss games use server-only `create_decided_swiss_game` and the shared progress projection; scheduled rounds book planned slots, applied self/play-by rounds create only fixtures inheriting their own round deadline; why: known players can book without automatic court assignments or duplicate games.
- Changing a generated later stage goes only through `replace_unplayed_structured_stage` (last stage, no played/booked games, audited); why: the structured spec is otherwise append-only.
- The live Swiss round count must stay equal in all three copies the running draw reads: `tournaments.builder_spec` stage `swissRounds`, `tournament_stages.config.swissRounds` and `club_champs.swiss_rounds[gn]`; `shortenSwissStage` writes all three but only ever lowers the count; why: the round gate, the standings and the server trigger each read a different copy.
- Owner-approved exact pairing charts in the Uitsig Club Champs are display-only templates in `src/lib/tournaments/swiss-uitsig-*-chart.ts`, gated to their current club/tournament/category/size/rounds, never written by fixture generation, and they skip strict slot-completeness validation; Ladies A's approved positions override RR display settings and bye substitutions, while saved games stay factual in Log/Calendar; why: category renumbering must not disable the approved preview or change live pairings.
- Nested jsonb setup writes (`tournaments.builder_spec` divisions/stages, `tournament_stages.config`) use a single-level `jsonb_agg(... ORDER BY ord)` over `WITH ORDINALITY` with a literal replacement value, never a nested correlated subquery; why: a nested correlated subquery silently replaced one division's `stages` with the whole divisions array, and `swissStageFor()` then rendered Swiss categories as round robin.

- Club-sponsored stock uses `bar_club_use` (bar permission): a `club_use` movement via `bar_stock_apply` plus a journal moving cost from the item's division purchase expense to `club_stock_expense`; why: giveaways must cut stock without touching sales, cash-ups or tips.

## Bar, counter and cash-up (moved from root)
- Cash-up writers and shared-hour closing enforce the final working staff member under the club cash-up lock; personal exits remain attendance-only and historical cash-ups stay intact. Why: inspection visits must not reconcile the till or end another person's working time.
- Cash-up summaries include all in-period cash-ledger movements, net of already counted cash sales/tips/payouts and excluding cash-up reconciliation journals; saved corrections retain the movement snapshot. Why: manual club cash expenses must reduce till expectations exactly once without rewriting sales or double-counting reconciliation.
- Zero-outstanding management tab removal uses an authenticated club-scoped RPC with a locked balance recheck including tips and auditable closure, never cascading deletion; tab additions lock the same parent row to prevent concurrent removal/sales races.
- Shared counters retain venue-scoped personal-PIN sessions with one active serving token, revalidated on selection; adding/selecting staff never ends attendance, shared End shift requires explicit person/all selection and confirmed device exit ends local participants; why: concurrent staff need separate hours and authoritative sale attribution without changing cash-up or payroll.
- Staff attendance is independent of PIN-session lifetime and cash reconciliation: club-scoped work shifts hold individual paid intervals and immutable own/hours/equal tip policies; shared tips use immutable cent allocations among staff with paid hours and one staff-earnings read model, and payroll snapshots an attendance cutoff; why: concurrent staff, late-earned tips and delayed approval must not duplicate hours or payments, and existing shift allocations must retain their original policy.
- Payday overrides are per-run review snapshots preserving original values; month-end preview uses read-only accruals and cannot confirm or prepare a run; why: checking pay must not rewrite attendance, future rates or financial records.
- Cash-up date labels use optional totals.cash_up_date metadata, never reconciliation cutoffs; why: correcting an evening label must not move sales between shifts or change opening cash.
- Counter tab-opening requests supply all six named arguments, with an explicit null member ID for visitors; why: older defaulted RPC overloads otherwise make visitor requests ambiguous.
- Cash-up UI exposes only View / edit and audited Save changes, with no Undo handler or deletion/reopening action; why: correcting a saved reconciliation must retain its shift record.
- Full saved cash-up edits use signed-in reason-required correction RPCs with expected-original snapshots, deterministic payout ownership and staff locks; append balanced reconciliation/payout adjustments, audit selected and next-shift opening corrections, preserve shift dates and later counted cash, and bound additions by historical and current earned-tip balances; why: all normal entry fields remain correctable without deleting a shift or silently distorting later reconciliations.
- The till cash-up history exposes the existing management report for signed-in platform admins; edits require server authorization and a reason, and counter PIN authorization stays unchanged; why: platform admins need direct access to corrections without granting anonymous management access.
- Club-sponsored stock shares private `_bar_club_use_post` between bar-authorised signed-in entries and atomic personal-PIN counter baskets; counter club/staff identity comes only from a locked valid session and private request rows enforce idempotency; why: one stock/accounting path, no admin bypass, customer tab, sale or duplicate deduction.
- Bar tabs left open past their Johannesburg opening day refuse new items and same-person new tabs via DB triggers; only an active club treasurer may grant a one-day override (bar_tab_day_overrides). Why: every writer (QR, counter, app) must be blocked, not just one screen.
- Playoff game length override lives on `tournaments.league_playoff_points_per_game` (per-category 7/11/15, null = same as pools); resolved by `playoffPointsPerGame` in effective-settings.ts and stage-scoring.ts, applied by the marker only to `isPlayoffGame` rows; why: pool games must keep the category PAR while QF/SF/Final can differ.
