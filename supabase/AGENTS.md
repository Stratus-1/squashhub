# Supabase rules

- Help Center ticket feed: support_threads insert/status change appends to service-role-only, append-only `help_center_ticket_outbox` in the same transaction; `help-center-ticket-feed` publishes only ticket UUID/status/revision/timestamps with static redacted text, HMAC-signed with dedicated `HELP_CENTER_HMAC_KEY`, fails closed without exact tenant scope + redaction policy, bounded backoff, retry cron armed only while pending; why: SquashHub stays authoritative and no customer content leaves the platform.
- Help Center delivery gate: `help_center_delivery_mode()` (paused default, pilot = `help_center_pilot_allowlist`, live) is enforced inside both `help_center_outbox_wake` and `help_center_outbox_claim`; live wake re-arms the existing retry job only while unheld work exists, and disarm deactivates it after drain. Backlog is preserved via `held_at`/`hold_reason`, never deleted or marked delivered; why: immediate delivery and bounded retries must recover after an empty queue without releasing held rows.
- Help Center publisher releases use the manually dispatched, main-only workflow in `.github/workflows/deploy-help-center-publisher.yml`; store its project-scoped deploy token only in the protected GitHub environment and follow `docs/HELP_CENTER_PUBLISHER_DEPLOYMENT.md`; why: deployment credentials and product delivery gates must remain separate.
- On-demand case-context reads do not use ticket pilot membership; workload/operator/tenant, held-event, active-ticket and latest-revision gates remain authoritative, with service-only bounded RPC projections; why: live human support must not depend on publisher pilots.

- IoT connectivity alerts reuse the Shelly Cloud `online` flag via `iot-connectivity-monitor` (cron poll, read-only), with per-device outage state in `club_iot_device_health` (grace period, one offline + one recovery email via club SMTP) and settings in `club_iot_alert_settings` (≤2 member recipients); unknown status never alerts; why: no competing health mechanism, no false/noisy alerts, club-scoped.

- Recurring-mandate lifecycle notices come only from DB trigger `notify_mandate_lifecycle` on `stitch_mandates` status changes, deduped by `mandate_lifecycle_notifications(mandate_id, event)` and sent in-app to `mandate_notification_recipients` (explicit `finance`/`recurring_payments` grants, not general admins); why: provider-confirmed status is the only trigger, one notice per event, least privilege.
- Log each user-facing change in `platform_change_log` (AI update writer uses only logged facts); member-wide platform updates are in-app only; why: no invented features, no mass member email/SMS.
- Comms template channel versions are always loaded filtered by the club's template IDs, and the onboarding template is identified by `action.key = register_existing_member`, never by display name; why: unfiltered reads hit the 1000-row API cap for platform admins and renames must not break lookup.
- Automatic notifications pass one BEFORE INSERT gate on `notifications` (`gate_auto_notifications`): tournament match messages come only from the draw-notice setting, booking made/cancelled notices follow `clubs.booking_confirm_enabled` and never fire for tournament (`champ:`/`sbs:`) bookings, and the reminders function skips those bookings; why: owner wants one simple switch per area.
- Server RPCs that insert pending member rows on behalf of someone else (e.g. `family_add_member`) must set transaction-local `app.family_add` so `club_members_guard_self_fields` leaves the row untouched; why: email auto-linking can make the row look like a self-application, corrupting role/approval or blocking the insert.

- Member "Available to spend" reuses the booking/bar gate inputs (allowance = recurring-plan fees + approved credit, minus owing) via existing read-only RPCs; why: the dashboard must never disagree with what the till or booking screen allows.
- `member_account_gate` adds issued unpaid invoices not yet due (Johannesburg) to spending allowance; why: no ledger change.
- Regional league fees: on-allocation drafts and imports share private `_league_fee_upsert_draft` (one unsent invoice per member/league/season; never deletes or touches sent/paid rows); why: team moves, drop-outs and re-imports must never double-charge or silently withdraw a fee.
- Booking writes enforce scheduled, unlinked championship allocations through `guard_scheduled_championship_booking`, using saved fixture duration without an admin bypass; why: capacity holds must not conceal already assigned games.
- Peak late-cancel limits/penalties are separate opt-in switches (OFF/0), shared by all court grids; penalties only for SquashHub-lit clubs, once per booking, never backdated; why: no accidental charges.
- AGM storage reads use the boolean-only exact attached-path definer check, never an invoker query of protected ballot rows; why: attendance-link downloads must work without exposing ballot or voter data.
- Nested jsonb setup writes (`tournaments.builder_spec` divisions/stages, `tournament_stages.config`) use a single-level `jsonb_agg(... ORDER BY ord)` over `WITH ORDINALITY` with a literal replacement value, never a nested correlated subquery; why: a nested correlated subquery silently replaced one division's `stages` with the whole divisions array, and `swissStageFor()` then rendered Swiss categories as round robin.
- Help Center product actions (`help-center-case-action`): only reply/set_status, same workload/IAP/operator/tenant gates as case-context plus `is_platform_admin` for the IAP email's single auth user; all writes go through service-only `help_center_apply_case_action` (latest-revision/held/active/idempotency checks, append-only body-free `help_center_case_actions`), reply email only to the ticket owner; why: SquashHub roles stay authoritative and existing triggers publish revisions.
- Gateway fees: estimates use the club fee rule (percentage + fixed + optional VAT); provider-reported actual fees are booked as one idempotent adjustment journal, never by editing the original fee lines. Why: the ledger must match provider payouts with a visible audit trail.
- Sandbox gateway payments (Stitch test mode / `test-` client, Yoco `sk_test_`) set `is_test` on the payment session at creation; settlement, the gateway-fee trigger and bar card verification skip every write for them (bar card checkout is refused), and verify responses return `test: true` for a TEST notice. Why: test money must never credit members, settle fees, post the ledger or trigger GoBook top-ups.
- Mobile reads of web-owned RPCs add a defaulted `p_sync_secret` path checked by `mobile_internal_secret_ok` plus the club/member match, never a parallel function; a supplied invalid secret never falls back to `auth.uid()`, because web and Player app must share one logic and web callers stay unchanged.
